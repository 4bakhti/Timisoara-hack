# Five-person usability pilot

Purpose: find and fix friction in the hands-free photography flow before judging. Five participants provide exploratory feedback, not statistical proof or accessibility certification. This is a proposed protocol; no participants or results have been collected in this review.

Ask each volunteer for permission to take part. Use anonymous labels P01–P05. Do not collect names, faces, contact details, recordings or photos for the results log. Let participants keep or delete their own pictures. Ask separately before retaining or publicly demonstrating a photo/recording.

## Task

Using a prepared phone, choose a suggested shot, follow one correction, ask what an instruction means, and take a photo. Give no instructions about which controls to press after the task begins. Record facilitator help if it is necessary.

If time permits, each participant tries the same task with voice on and with touch/text guidance. Alternate the order between participants to reduce learning effects. Keep scene, device, idea difficulty and success criteria as comparable as possible. Record differing conditions instead of treating them as controlled. Both modes use the same real planning/tracking, or both use the same clearly identified test setup.

Record locally: participant label, version, mode order, device/browser, task completed (yes/no), time from ready camera to capture, touches after initial permissions/start, facilitator interventions, failed voice actions and a 1–5 ease rating. Distinguish an attempted voice action from a successfully executed one.

Ask afterward:

1. Which instruction was hardest to follow?
2. When did you stop trusting what the coach said?
3. What is the one change that would make you use it again?

## Iterate

Identify the most frequent or most disruptive problem. Change one relevant behavior, record the commit, and retest that behavior with available participants. Do not attribute all differences to the change if the participants, scene or device also changed.

Report counts with denominators, e.g. “3 of 5 completed without facilitator help,” only if measured. Report median task time alongside failures rather than excluding unsuccessful attempts silently. Avoid invented before/after percentages. Preserve negative results: they explain why the next iteration improved.

Store raw notes outside Git, for example in the already ignored `reports/` directory after checking ignore rules in your clone. Publish only a consent-appropriate aggregate summary: number tested, exact task, conditions, biggest failure, change made, retest result and limitations. Never substitute synthetic events or a scripted demo for real-user validation.
